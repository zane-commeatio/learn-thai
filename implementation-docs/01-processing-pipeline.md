# 01-processing-pipeline

This document defines a ticket-by-ticket implementation plan for the upload processing pipeline.
Order is mandatory unless explicitly noted.

## Conventions

- Ticket IDs use `PP-XX`.
- Each ticket includes exact acceptance criteria.
- “Done” means all acceptance criteria pass in CI.

---

## PP-01: Backend Bootstrap

### Scope
- Initialize backend project structure.
- Add test runner, lint/typecheck setup, env config loader, and base route wiring.
- Add `GET /api/mobile/health`.

### Dependencies
- None

### Acceptance Criteria
- Project runs tests via one command (for example `npm test`).
- `lint + typecheck` command exists and passes on clean checkout.
- `GET /api/mobile/health` returns HTTP 200 with `{ status, apiVersion }`.
- CI config executes lint/typecheck/tests.

---

## PP-02: Core Contracts and State Machine

### Scope
- Define shared schemas/types for:
  - `clips`
  - `processing_jobs`
  - stage enum: `audio`, `asr`, `segment`, `tokenize`, `gloss`, `finalize`
  - state enum: `uploaded`, `processing`, `needs_review`, `failed`, `manual_intervention`
- Define standard API error envelope.

### Dependencies
- PP-01

### Acceptance Criteria
- Runtime validation exists for all request/response payloads in this slice.
- Invalid enum values are rejected with `invalid_request`.
- Unit tests verify legal stage/state transitions.
- Error envelope is consistent across all implemented endpoints.

---

## PP-03: Persistence Foundation (Neon)

### Scope
- Create initial migrations for minimum pipeline tables:
  - `clips`
  - `processing_jobs`
  - `audit_log`
- Implement repository interfaces and DB-backed implementations.
- Define these tables in Drizzle schema files and generate migrations from schema.

### Dependencies
- PP-02

### Acceptance Criteria
- Migration up/down works on a clean DB.
- Repositories support create/read/update used by this vertical slice.
- Integration tests run against test DB and pass.
- No manual SQL migration files are authored; migrations are generated by Drizzle.
- No hand-edited generated migration SQL in the PR.
- CI fails when migration SQL changes without corresponding schema file changes.

---

## PP-04: Create Clip Endpoint

### Scope
- Implement `POST /api/creator/clips` with validation and DB persistence.
- Persist required fields for processing kickoff (`source_type`, `rights_status`, metadata).

### Dependencies
- PP-03

### Acceptance Criteria
- Valid request returns HTTP 201 with `clipId`.
- Missing/invalid required fields return HTTP 400 with standard error envelope.
- Created clip row exists in DB with expected defaults.
- Endpoint integration tests cover success + validation failures.

---

## PP-05: Upload Complete Endpoint (Enqueue Only)

### Scope
- Implement `POST /api/creator/clips/{clipId}/upload-complete`.
- Create processing job row in `processing` state (`stage=audio`).
- Enqueue one processing message; do not execute pipeline inline.

### Dependencies
- PP-04

### Acceptance Criteria
- Existing clip returns HTTP 202 and creates exactly one new processing job row.
- Nonexistent clip returns HTTP 404.
- Exactly one queue message is enqueued per request.
- Duplicate identical requests are idempotent or safely rejected (explicit behavior documented + tested).

---

## PP-06: Queue Worker Runner and Job Locking

### Scope
- Implement queue consumer that loads job and runs stage executor.
- Add job-locking/claim logic to prevent double execution.
- Write audit log events for stage transitions.

### Dependencies
- PP-05

### Acceptance Criteria
- Same message cannot process the same job concurrently.
- Stage updates are persisted with monotonic progression.
- Audit entries are written for start, stage changes, completion/failure.
- Worker integration test validates single-run behavior under duplicate delivery simulation.

---

## PP-07: Stage Adapter - Audio Extraction/Normalization

### Scope
- Implement stage wrapper for audio extraction/normalization from uploaded media.
- Store artifact refs for downstream stages.

### Dependencies
- PP-06

### Acceptance Criteria
- Successful job advances from `audio` to `asr`.
- Stage failures set job state to `failed` and persist `error_payload`.
- Stage duration and outcome are logged.
- Integration tests cover success + failure branch.

---

## PP-08: Stage Adapter - ASR

### Scope
- Implement ASR adapter boundary (Whisper integration point).
- Request word-level timestamps and store raw ASR output ref.

### Dependencies
- PP-07

### Acceptance Criteria
- ASR success advances job stage to `segment`.
- ASR timeout/provider errors set job to `failed` with structured error code.
- No automatic retry loop is triggered on ASR failure.
- Adapter tests cover success, timeout, provider error mapping.

---

## PP-09: Stage - Segment Shaping

### Scope
- Transform ASR output into transcript segments.
- Enforce deterministic ordering/indexing.

### Dependencies
- PP-08

### Acceptance Criteria
- Identical ASR input yields byte-equivalent segment output.
- Invalid ASR payload fails deterministically with explicit error code.
- Stage transitions to `tokenize` on success.
- Snapshot tests verify deterministic segment output.

---

## PP-10: Stage - Tokenization and Stable IDs

### Scope
- Implement deterministic tokenization.
- Generate stable token IDs from `(clipVersion + token_index)` rule.

### Dependencies
- PP-09

### Acceptance Criteria
- Re-running tokenization with same inputs yields identical token IDs/order.
- Token ordering matches transcript ordering.
- Stage transitions to `gloss` on success.
- Unit tests verify determinism and ID stability.

---

## PP-11: Stage - Gloss Prefill

### Scope
- Integrate LEXiTRON prefill lookup.
- Attach gloss outputs to token IDs.

### Dependencies
- PP-10

### Acceptance Criteria
- Tokens with lexicon matches receive glosses.
- Missing entries are handled without failing whole job (documented fallback).
- Stage transitions to `finalize` on success.
- Tests verify lookup match + no-match behavior.

---

## PP-12: Finalize Stage and Review-Ready Persistence

### Scope
- Persist final editor payload artifacts.
- Mark processing job `needs_review`.
- Write final audit events.

### Dependencies
- PP-11

### Acceptance Criteria
- Completed jobs end in `state=needs_review`, `stage=finalize`.
- Final payload is persisted and retrievable by clip ID.
- Audit log contains completion event with actor/system marker.
- End-to-end test passes from enqueue through finalize.

---

## PP-13: Processing Status Endpoint

### Scope
- Implement `GET /api/creator/clips/{clipId}/processing`.
- Return latest `state`, `stage`, `error`.

### Dependencies
- PP-12

### Acceptance Criteria
- Existing clip with active/completed job returns latest status.
- Existing clip with no job returns initial uploaded-like status contract.
- Unknown clip returns HTTP 404.
- Endpoint integration tests cover all three cases.

---

## PP-14: Manual Retry Endpoint

### Scope
- Implement `POST /api/creator/clips/{clipId}/retry-processing`.
- Create a new processing attempt from existing upload artifacts.

### Dependencies
- PP-13

### Acceptance Criteria
- Retry creates a new processing job row linked to same clip.
- Previous failed job history remains intact.
- Retry on clip with no upload artifacts returns conflict-style error.
- No automatic retries are introduced by this endpoint.

---

## PP-15: Observability and Operational Controls

### Scope
- Add structured logs for request/job flows.
- Add basic metrics:
  - job success/failure counts
  - stage durations
  - queue lag/backlog
- Add concurrency caps for worker processing.

### Dependencies
- PP-14

### Acceptance Criteria
- Logs include required fields (`request_id`/`job_id`, `clip_id`, stage/state, error code if present).
- Metrics are emitted for every completed or failed job.
- Concurrency cap is configurable and enforced.
- Load test demonstrates stable processing under configured concurrency.

---

## PP-16: End-to-End Validation and Baseline Performance

### Scope
- Validate full flow in staging-like environment:
  - create clip
  - upload complete
  - queued processing
  - `needs_review`
  - status polling
  - manual retry
- Define baseline performance budget for this slice.

### Dependencies
- PP-15

### Acceptance Criteria
- E2E test suite passes on CI and staging.
- Determinism check: repeated runs with same input produce same derived artifacts.
- Throughput benchmark report is produced and archived.
- Operational runbook references are linked for retry/outage handling.

---

## Definition of Done (Pipeline Slice)

The upload processing vertical slice is complete when:
- PP-01 through PP-16 are completed.
- CI gates pass (`lint + typecheck + tests`).
- No unresolved P1/P2 defects remain in this slice.
- Docs are updated for any implementation deviations.
